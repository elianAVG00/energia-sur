# Design: CU05 meter readings

## Context

CU04 supplies stable account-owned meters; CU09 supplies sessions and Origin/CSRF protection. PostgreSQL and a non-root FastAPI Docker runtime already exist. CU05 is not implemented. The user explicitly authorized BUILD and approved D14/D15; runtime verification and unresolved safety gates remain mandatory.

## Goals / Non-Goals

**Goals:** private, versioned reading history and manual confirmation, optional private image and local, abstaining OCR.

**Non-Goals:** no independent blur detector, automatic OCR retries, external OCR APIs, reading deletion, physical meter replacement, CU06/CU07 work or inferred consumption/rollover. No broad OCR accuracy claim from one photo.

## Decisions

### OCR: local Tesseract and manual crop (D01–D04, D10)

Run Tesseract inside Docker, without external APIs; the user explicitly requests OCR and manually crops the register. Limit photo bytes to 5,000,000 and do not automatically retry. A digit whitelist or segmentation mode can assist after cropping but cannot establish that the chosen region is the kWh register. Preserve original color/context in memory. **Latest BUILD instruction:** exclude clearly separable red fractional digits; abstain if their boundary is uncertain. OCR does not save; a suggested integer remains editable and requires explicit confirmation.

| Outcome | Meaning and behavior |
| --- | --- |
| Success | A single sufficiently reliable register value is suggested, without saving; user may edit and confirm. |
| Abstention | Multiple candidates, wrong/partial crop, ambiguous wheels, red fraction boundary or low confidence: no suggestion and the exact U13 fallback message. |
| Engine failure | Unavailable engine, decoding error or timeout: no suggestion, same fallback; manual entry remains available. |
| Coverage limit | One example cannot calibrate confidence or establish false-positive rates, resilience across meter styles or correct identification of identifiers. No general accuracy claim. |

The exact fallback is “No pudimos identificar con seguridad la lectura del medidor. Intentá subir una fotografía más clara o ingresá manualmente el valor en kWh”. The user selects the region intended as the register. The implementation accepts one digit token passing its threshold and red-overlap checks; it does not independently verify register identity, detect all identifiers, or establish that every wheel is complete. It abstains when its implemented checks detect uncertainty. A confident suggestion can therefore still be wrong, including when an identifier was selected; the owner must review and explicitly confirm or correct it. Red detection is heuristic and does not establish the absence of every fractional digit. No representative accuracy is claimed. [Tesseract quality](https://github.com/tesseract-ocr/tessdoc/blob/main/ImproveQuality.md) and [TSV output](https://github.com/tesseract-ocr/tessdoc/blob/main/Command-Line-Usage.md) were consulted via Context7 on 2026-11-08.

**M1, superseded in part by the subsequent BUILD instruction:** OCR may abstain whenever it cannot identify the reading with sufficient confidence; manual entry remains authoritative. M1 does not replace an actual Tesseract attempt when safe admission permits it. No unverified accuracy is claimed.

For the academic demo, enforce 20,000,000 decoded pixels **for OCR**, one OCR job deployment-wide, a 5-second engine deadline and a 256 MiB per-engine-process memory ceiling; abstain safely on violation. The user subsequently approved a separate 40,000,000 decoded-pixel per-frame limit for stored photos and direct declaration of the already-locked Pillow 13.0.0. Supported photos within 5,000,000 bytes and 40 MP can still be saved without OCR when they exceed the OCR pixel limit. These are operational guardrails, not accuracy measurements. A deployment-wide supervised job boundary owns admission until all descendants are confirmed dead, including after API-worker death; saturation yields fallback without retry. At startup/recovery, refuse admission until previous job termination is confirmed; fail closed if supervision cannot ensure this. Run decoding in a separately bounded worker: cap that worker at 512 MiB and the streamed JSON request at 7,000,000 bytes. The 256 MiB bound is not a total job/server memory bound. Reap the entire process group on timeout before releasing admission. Do not log images, crop or OCR text or expose internal errors; enforce limits with mechanisms verified on the target Docker platform or fail closed.

**BUILD implementation:** OpenCV headless 4.12.0.88 and its locked NumPy dependency are used inside the bounded child for inversion and selective resizing; crops at least 80 pixels high are not enlarged because interpolation distorted a browser-rendered digit. The child acquires a nonblocking flock on a stable file in the shared private photo volume and passes the locked descriptor to Tesseract; Linux parent-death signals kill descendants when their parent dies, while inherited locking prevents admission during process teardown. All OCR workers must share that volume and lock file. Saturation and failures abstain. Isolated multi-container tests exercised saturation, process death, recovery and restart; runtime measurements confirmed 512 MiB worker and 256 MiB engine address-space limits. Docker Compose sets a 1 GiB backend memory limit, zero swap and zero core dumps. The endpoint checks cgroup v2 swap limit and core limit before it buffers the request and abstains if they cannot be verified; this does not prevent upstream HTTP buffering, so deployment must enforce those limits before accepting traffic. The regression image now reads correctly, but confidence remains no correctness guarantee. A subsequent independent review and its findings are recorded below.

**Focused review follow-up:** a single independent review found that image validation previously preceded OCR admission. It now runs inside the locked, parent-death-guarded worker; invalid photos and crop geometry return sanitized 422 and oversized OCR frames still abstain. Saturation and death during image validation have focused tests. The review also identified a material unresolved conflict: the delta prohibits inclusion of any fractional digit, but fixed color thresholds cannot prove that all red fractions are detected. Do not sync or archive until the user resolves that contract conflict; the real-photo abstention remains accepted.

**Human acceptance checkpoint:** the user accepted the OCR worker security risk and real-photo abstention, initially requesting no further independent review; that request was subsequently replaced by an explicit request for one focused review, which was performed. The development backend was rebuilt and recreated with its existing DB connection, original DB container and photo volume; effective limits, OCR dependencies, DB ping and synthetic worker OCR passed. Authenticated DEV browser tests now pass using synthetic accounts.

The user authorizes synthetic image fixtures and local-only verification using the supplied real photograph, selecting the whole supplied image as the crop. Never add real photos to the repository, logs or artifacts. Synthetic and mocked tests cannot establish representative OCR accuracy. Missing required security and integration tests remain BLOCKED, not waived.

**Local OCR research, 2026-11-09:** the user requests supporting the supplied image without requiring a better one and excluding the red decimal region. A network-disabled Docker experiment compared Tesseract 5.3 with OpenCV 4.12 preprocessing (automatic dark-region candidates, 4x cubic scaling, CLAHE, Otsu/adaptive thresholds, both polarities, PSM 7/13) against RapidOCR 1.4.4 / ONNX Runtime with Paddle-derived models and the same candidate detector. Tesseract produced conflicting four-digit candidates at confidence zero; RapidOCR produced no numeric result on the automatic candidates and took 9.47–34.90 seconds per tested region. Its whole-image numeric detections cannot be assumed to be register values. The user later selected Tesseract plus OpenCV and supplied a provisional visual reference, not a guaranteed result. Reasonable editable candidates need not achieve perfect confidence, but inconsistent results and uncertain red exclusion still require abstention. Neither experiment establishes a reliable integer/red-decimal boundary or meets the approved five-second job behavior as demonstrated. EasyOCR and full PaddleOCR were researched but not run. Preserve manual confirmation and fail-closed behavior until suitable preprocessing and crash-safe admission are demonstrated.

### Timestamp, identity and concurrency (D05–D07, D11–D12)

Require ISO 8601 offset-aware date/time with seconds and no fractional seconds; reject missing offsets, fractional seconds and future instants against the server clock. Persist UTC seconds and display in `America/Argentina/Buenos_Aires`. PostgreSQL MUST enforce uniqueness of `(meter_id, normalized instant)` atomically, including simultaneous writes. Different meters may share an instant. Compare against the most recent earlier reading of that meter, excluding the record being edited; a lower value triggers a UI warning but can be confirmed. Meter identity remains stable; no physical replacement.

Use the proposed contract below, not an existing implementation. Reuse authenticated session, server-side meter/domicile/account ownership, CU04's indistinguishable missing/foreign resource treatment and CU09 Origin/CSRF protection for unsafe operations, including OCR POST. Private photo retrieval is authenticated and ownership-checked; do not expose a public volume or filesystem paths. Every PATCH, including unchanged fields, atomically checks the supplied version and increments it on success; stale requests return 409 `VERSION_CONFLICT` without mutation.

#### Proposed API contract

Backend paths below; browser uses existing `/api` proxy prefix. JSON rejects extra fields and booleans as integers. IDs are opaque strings. Reading representation: `{id, meter_id, recorded_at, value_kwh, has_photo, version}`, where `recorded_at` is UTC ISO with seconds and `Z` and `version` starts at 1. **D14:** `value_kwh` is a nonnegative decimal digit string end-to-end, including OCR suggestions, persisted as exact PostgreSQL numeric; no floating-point conversion. Dates and ownership are server-validated. JSON photo bytes use `photo_base64` (standard base64, no data URL); no filename or raw path is stored or returned. Cap streamed encoded request bodies before full buffering (7,000,000 bytes), decode photo in bounded memory; photo data itself is capped at 5,000,000 bytes. Read/chunk count in memory only: multipart spooling, swap, core dumps and native tool temp files must not persist unconfirmed images. If this cannot be ensured, OCR is unavailable and fails closed.

| Method and path | Request | Success |
| --- | --- | --- |
| `POST /meters/{meter_id}/readings` | `Idempotency-Key` stable per creation attempt; `{recorded_at, value_kwh: string, confirmed: true, photo_base64: string|null}` | 201 Reading; same key/payload replays original result |
| `GET /meters/{meter_id}/readings` | none | 200 `Reading[]`, descending instant |
| `GET /meters/{meter_id}/readings/{reading_id}` | none | 200 Reading |
| `PATCH /meters/{meter_id}/readings/{reading_id}` | `{version, recorded_at, value_kwh, confirmed: true, photo_action: "keep"|"remove"|"replace", photo_base64: string|null}`; replacement requires bytes, other actions require null | 200 Reading, incremented version |
| `POST /meters/{meter_id}/readings/ocr` | `{photo_base64, crop: {x, y, width, height}}`, integer pixel coordinates in original image | 200 `{status: "suggested", value_kwh: string}` or `{status: "abstained", value_kwh: null, message: string}` |
| `GET /meters/{meter_id}/readings/{reading_id}/photo` | none | 200 image bytes with verified content type and `Cache-Control: no-store` |

Crop must be nonempty, inside decoded original bounds, no automatic retry; API holds full source and crop only during the request. `keep` preserves, `remove` clears the association, `replace` publishes a new object. Cancel means no save request and no server-persisted draft. There is no reading DELETE. Missing session 401; untrusted Origin/invalid CSRF for unsafe requests 403; with valid security credentials, missing/foreign/mismatched meter, reading or photo use identical 404. Wrong content type returns 415; malformed JSON, conflicting fields, invalid image/value or crop returns sanitized 422; byte/request caps return 413. First perform authentication, unsafe-request Origin/CSRF and meter ownership checks, then bounded body parsing, then reading ownership/version and body validation; stale PATCH takes precedence over duplicate detection. Duplicate timestamp returns 409 `{detail: string, code: "DUPLICATE_READING"}`; stale PATCH returns 409 `{detail: string, code: "VERSION_CONFLICT"}`. Definite rejection or rollback does not mutate readings; a lost connection during COMMIT may have committed despite an error response. After an indeterminate PATCH the client must GET and reconcile version/data before retrying. For an indeterminate create retry the exact payload with the same idempotency key. Engine failure, pixel limit and saturation produce `abstained` and the exact fallback. Database/storage failure returns sanitized 503. All private JSON and image responses are non-cacheable.

### D15 transactional create idempotency

The client generates one UUID key per creation attempt and keeps it stable across retries, including unknown commit outcomes. Require a canonical lowercase UUID string; missing/invalid keys return 422. Scope keys to authenticated account plus meter and retain records for the lifetime of the reading; deletion is not supported. Compare exact validated input strings for `recorded_at` and `value_kwh`, confirmation and decoded photo bytes (not JSON formatting or base64 presentation); differences are different payloads. Decimal values contain 1–131072 ASCII digits, PostgreSQL numeric's integral capacity, with no sign, spaces or separators; responses use canonical digits without leading zeroes except `0`. Values over that capacity return 422. Persist the key, a SHA-256 fingerprint of length-delimited input fields including a hash of decoded photo bytes, and the original creation response atomically in PostgreSQL with the reading. Concurrent same-key/same-payload requests wait for the transaction and replay that original response; same key and different payload returns 409 `IDEMPOTENCY_KEY_REUSED` without mutation. After rollback the same attempt may be retried; after an unknown commit, replay resolves the outcome. Never log key or payload; perform ownership checks before lookup. Photo publication and recovery retain the previously specified durable-object/unknown-commit safeguards.

### In-memory OCR and persistent photos (D08–D09, D13)

Before confirmation, OCR image bytes and derivatives remain in memory only; no file, persisted draft, logs or durable upload until confirmation. Ensure image-decoding and Tesseract invocation comply (e.g. pipes or explicitly memory-backed execution with no disk spill); process crash and resource limits must not silently persist them. Do not treat a local disk temporary directory as memory. Confirmed photos use the approved FastAPI-managed persistent Docker volume with PostgreSQL metadata and private ownership checks.

Use opaque random immutable object names on a private backend-managed volume; never trust client paths. A stable, never-replaced lock file is shared by all backend workers and maintenance processes. Acquire a fixed PostgreSQL session advisory lock on an explicitly checked-out physical connection, then the filesystem lock, then any D15 transaction lock. Bind the ORM session to that same retained connection and keep it checked out through commit/rollback and reference-checked cleanup; explicitly unlock on that connection before returning it to the pool. Invalidate rather than pool a connection if unlock or connection health is uncertain. Do not assume `Session.commit()` preserves a session-owned pooled checkout. Photo reads retain the required locks until their stream closes. If locks or durability semantics are unavailable, fail closed.

Under that lock order, determine D15 replay versus a new attempt before publishing an object. Split the existing combined creation primitive into a replay/lock step and a staging step, retaining the same transaction and lock until completion. A replay must not publish another object. For a confirmed new create/replacement exclusively create a unique managed temporary file with no symlink following on the same volume and fsync it; publish with a verified atomic **no-replace** operation, choose a fresh random name on collision, and fsync the directory before the version-qualified database commit. Ordinary overwrite-capable rename is not sufficient. Keep the previous file until confirmed commit; on definite rollback/stale conflict remove the new object only after a committed-reference check. After commit, remove the old file only if no DB reference exists. Synchronize directory changes after deletion. Remove-photo commits a null association first, then reference-checked cleanup. Never follow symlinks or delete a live object.

For photo reads, authenticate then obtain the DB advisory lock followed by the filesystem lock; while holding both, recheck the meter/reading ownership and current photo association, open the immutable object and stream it while locks remain held, releasing both on completion or client disconnect. No reader can observe an association then wait for a later-deleted object; no filesystem→DB reverse ordering is permitted. Bound slow reads or fail closed if the streaming lifecycle cannot reliably release locks.

If commit outcome is unknown (connection lost during COMMIT), retain both files: never infer rollback. Invalidate the failed database connection and release the filesystem lock without attempting to reacquire the database lock while holding it; doing otherwise can deadlock a new holder of the database lock. A later reconciliation independently obtains the PostgreSQL advisory lock and then the filesystem lock, verifies that the original database session and transaction have ended, checks committed references and removes only proven unreferenced objects. The fixed lock must never be voluntarily released before the original transaction resolves; on a verified single-primary PostgreSQL topology, acquisition by reconciliation proves the former lock-holding session has ended or released it after resolution. If topology, session resolution or lock acquisition cannot be established, do not delete anything. This includes process death while COMMIT is in flight.

On process crash, startup or an explicitly invoked local maintenance pass obtains the same DB and filesystem locks and scans both managed temporary and final names against committed DB references, deleting only unreferenced files; if DB is unavailable do nothing. Deletion failures are logged without names or sensitive content and retried by the next explicit pass/startup, not by a worker/queue. Missing referenced bytes require recovery, not silent repair. For a matched backup, stop all backend workers and other writers, drain/terminate their transactions and photo reads, prevent restart, verify the DB advisory and filesystem locks are available, then take a PostgreSQL-consistent backup and copy the volume while the services remain stopped. Fail closed if quiescence cannot be proven; restore both as a matched pair while stopped, then check every DB photo reference exists before restarting. No backup, cleanup or restore is authorized now.

## Risks / Trade-offs

- [Wrong crop or high-confidence identifier] → manual review is not proof; abstain when uncertain, preserve explicit confirmation, document limited one-photo evidence.
- [Native tool spills sensitive bytes to disk] → require true in-memory processing and verify the execution path and no logs or external transfer.
- [Crash or race between DB and volume] → preserve the old object until commit, design idempotent recovery and cross-account-safe cleanup, and test failure points after authorization.
- [Unsafe or expensive image] → enforce the stated request, decode, OCR memory/time and deployment-wide concurrency bounds; validate enforcement on the actual runtime.

## Migration Plan

Future implementation requires a separately authorized additive migration, volume, coherent backups and tested non-destructive recovery. This review executes none of them; never delete existing data as an assumed rollback.
